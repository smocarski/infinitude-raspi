# Infinitude MQTT Control Specification

Version: derived from source as of 2026-09-16 (branch `bookworm-slim`).

This document describes the complete MQTT interface exposed by **Infinitude**, a
local replacement server for Carrier Infinity / Bryant Evolution thermostats.
It is written for any MQTT-speaking controller (openHAB, Node-RED, a script,
etc.). Home Assistant's auto-discovery is also emitted, but it is entirely
optional and is confined to [Appendix A](#appendix-a-home-assistant-discovery);
nothing in the control interface depends on it.

---

## 1. Overview

Infinitude sits between the physical thermostat and Carrier's cloud. The
thermostat polls Infinitude over HTTP; Infinitude serves it the configuration it
should apply. MQTT is a **secondary, optional** control surface layered on top:
publishing a command topic edits Infinitude's stored configuration, and the
thermostat picks that change up on its next poll.

Key properties, all of which matter for a controller implementation:

| Property | Value |
|---|---|
| MQTT client | `Net::MQTT::Simple` (Perl) — Infinitude connects **out** to your broker |
| Protocol version | MQTT 3.1.1 |
| QoS | **0 only**, for every publish and every subscribe. There is no QoS setting. |
| State topics | **Retained** |
| Availability topic | **Retained**, with a retained Last Will |
| Command topics | Infinitude never publishes to them; you must publish **non-retained** |
| Acknowledgement | **None.** There is no ack, error, or result topic. |
| Payload encoding | Plain UTF-8 strings. No JSON anywhere except discovery configs. |
| Enabled when | `MQTT_BROKER` is set; otherwise the whole subsystem is a no-op |

Two independent topic roots are used:

- **Base root** (`MQTT_TOPIC`, default `infinitude`) — all state and command
  topics. This is the only root a non-Home-Assistant controller needs.
- **Discovery root** (`MQTT_PREFIX`, default `homeassistant`) — Home Assistant
  discovery configs, plus the birth topic Infinitude listens on.

Throughout this document, `<base>` means the value of `MQTT_TOPIC` (default
`infinitude`) and `<N>` means a **1-based** zone number.

## 2. Connection and configuration

Every setting can be given either as an environment variable or as a key in
`infinitude.json` in the working directory. The environment variable wins when
it is set and non-empty.

| Environment variable | JSON key | Default | Meaning |
|---|---|---|---|
| `MQTT_BROKER` | `mqtt_broker` | *(unset — MQTT disabled)* | Broker address. `host` or `host:port`. Port defaults to 1883. |
| `MQTT_USER` | `mqtt_user` | *(unset)* | Username. Setting it enables MQTT authentication. |
| `MQTT_PASS` | `mqtt_pass` | `''` | Password. Only used when `MQTT_USER` is set. |
| `MQTT_TOPIC` | `mqtt_topic` | `infinitude` | Base root for state and command topics. |
| `MQTT_PREFIX` | `mqtt_prefix` | `homeassistant` | Discovery root and birth topic root. |

Example (`docker-compose.yaml` style):

```yaml
environment:
  - MQTT_BROKER=192.168.1.10:1883
  - MQTT_USER=infinitude
  - MQTT_PASS=secret
  - MQTT_TOPIC=infinitude
```

### Limitations to plan around

- **No TLS.** The broker string accepts an `ssl:` prefix, but it only suppresses
  an insecure-login warning flag; the client instantiated is always the
  plaintext one. Treat TLS as unsupported and keep the broker on a trusted LAN.
- **Credentials are sent in the clear** over that plaintext connection.
- **No client-id option.** The client id is generated by the library. If you run
  two Infinitude instances against one broker they may collide.
- **No configurable publish interval.** The timers (1 s connection tick, 8 s
  startup announce, 60 s change poll) are hardcoded.
- **No port key.** The port is part of the broker string.
- **Do not set `MQTT_PREFIX` equal to `MQTT_TOPIC`.** Doing so makes the
  availability topic (`<base>/status`) and the discovery birth topic
  (`<prefix>/status`) the same string, and Infinitude's own retained `online`
  message will re-trigger a full re-announce on every reconnect.

### Connection behaviour

Infinitude polls the connection once per second. On a down→up transition it
re-announces availability, discovery, and full state. If the broker is
unreachable at startup it logs a warning and keeps retrying indefinitely; a
still-down broker is re-logged every 5 minutes. A missing broker never blocks
thermostat control — the TCP connect is bounded at 5 s so the event loop keeps
serving the thermostat.

## 3. Availability

```
<base>/status
```

| | |
|---|---|
| Payload | `online` or `offline` |
| Retained | Yes |
| Published | `online` at startup, on reconnect, and as a 60 s backstop |
| `offline` | Published by the **broker** as Infinitude's Last Will when the connection drops |

A controller should treat every state value as stale whenever this topic reads
`offline`. Because both the `online` message and the Will are retained, a
freshly connected subscriber always gets a current answer immediately.

## 4. Topic map

`<N>` is a 1-based zone number. Only zones the thermostat reports as enabled are
published — see [§8](#8-zones).

### 4.1 State topics (published by Infinitude, all retained, QoS 0)

| Topic | Payload | Notes |
|---|---|---|
| `<base>/status` | `online` \| `offline` | Availability / LWT |
| `<base>/zone/<N>/current_temp` | number as string, e.g. `71.0` | Measured zone temperature. Empty string if the zone reports no reading. |
| `<base>/zone/<N>/humidity` | integer as string, e.g. `44` | Measured relative humidity, percent |
| `<base>/zone/<N>/mode/state` | `off` \| `heat` \| `cool` \| `heat_cool` | System-wide, republished per zone. `heat_cool` is the thermostat's `auto`. |
| `<base>/zone/<N>/temp/state` | number as string **or the literal `None`** | Single target setpoint. See warning below. |
| `<base>/zone/<N>/temp_low/state` | number as string, e.g. `68.0` | Heat setpoint (`htsp`) of the currently active activity |
| `<base>/zone/<N>/temp_high/state` | number as string, e.g. `75.0` | Cool setpoint (`clsp`) of the currently active activity |
| `<base>/zone/<N>/fan/state` | `auto` \| `low` \| `medium` \| `high` | Fan setting of the active activity |
| `<base>/zone/<N>/action` | `heating` \| `cooling` \| `preheating` \| `idle` | What the equipment is doing right now |
| `<base>/zone/<N>/preset/state` | `schedule` \| `home` \| `away` \| `sleep` \| `wake` \| `hold` \| `hold_until` | Hold / schedule state. See [§6.9](#69-presetstate). |
| `<base>/system/oat` | number as string | Outdoor air temperature |
| `<base>/system/filtrlvl` | integer as string | Filter life consumed, percent |
| `<base>/system/uvlvl` | integer as string | UV lamp life consumed, percent |
| `<base>/system/humlvl` | integer as string | Humidifier pad life consumed, percent |
| `<base>/system/ventlvl` | integer as string | Ventilator filter life consumed, percent |
| `<base>/system/humid` | `on` \| `off` | Humidifier state |

> **`temp/state` is not always a number.** When the system mode is `heat` it
> carries the heat setpoint, when `cool` the cool setpoint, and in **every other
> mode (`off`, `auto`/`heat_cool`) it is the literal four-character string
> `None`.** A controller that binds this to a numeric item must either guard
> against `None` or ignore this topic entirely and use `temp_low/state` and
> `temp_high/state`, which are always numeric. Using the low/high pair is the
> recommended approach.

The six `<base>/system/*` topics are published **only when the value is
non-empty**. A system without a UV lamp or ventilator will simply never produce
those topics; do not wait on them.

### 4.2 Command topics (published by the controller, non-retained, QoS 0)

| Topic | Accepted payloads |
|---|---|
| `<base>/zone/<N>/mode/cmd` | `off`, `heat`, `cool`, `heat_cool`, `auto` |
| `<base>/zone/<N>/temp/cmd` | a number, e.g. `70` or `70.5` |
| `<base>/zone/<N>/temp_low/cmd` | a number |
| `<base>/zone/<N>/temp_high/cmd` | a number |
| `<base>/zone/<N>/fan/cmd` | `auto`, `low`, `medium`, `high` |
| `<base>/zone/<N>/preset/cmd` | `schedule`, `none`, `home`, `away`, `sleep`, `wake`, `hold`, `hold_until` |

All enum payloads are matched **case-insensitively**. Numeric payloads must
match `^[0-9.]+$` exactly — see [§5](#5-payload-grammar-and-error-handling).

> **Never publish a command with the retain flag set.** Infinitude subscribes at
> QoS 0 and re-subscribes on every reconnect. A retained command is redelivered
> each time, which silently re-applies the command — most damagingly, a retained
> setpoint will re-assert a manual hold every time the broker connection blips.

---

## 5. Payload grammar and error handling

- **Enums** are lowercased and looked up in a fixed table. An unrecognised value
  is **silently discarded**.
- **Numbers** must match the regular expression `^[0-9.]+$` — digits and dots
  only. This means:
  - `70`, `70.0`, `70.5` are accepted.
  - `+70`, `-5`, ` 70` (leading space), `70F`, `seventy`, `None`, `null`, `{"t":70}`
    are all **rejected and silently discarded**.
  - Negative temperatures cannot be expressed. This only matters for a Celsius
    system, where setting anything below 0 °C is impossible over MQTT.
- **There is no acknowledgement, error, or status-of-last-command topic.** A
  rejected payload is indistinguishable from a lost one. The only feedback is
  the corresponding `.../state` topic being republished (see
  [§7](#7-publish-timing-and-consistency)).
- A controller that needs confirmation must read back the relevant `state` topic
  and compare. Allow at least 2 s: the optimistic republish is immediate, but it
  reflects Infinitude's intent, not the thermostat's reality.

## 6. Command reference

### 6.1 `<base>/zone/<N>/mode/cmd` — system mode

| Payload | Effect |
|---|---|
| `off` | System off |
| `heat` | Heat only |
| `cool` | Cool only |
| `auto` | Auto changeover |
| `heat_cool` | Alias for `auto` (Home Assistant's spelling) |

> **This command is SYSTEM-WIDE, not per-zone.** The zone number in the topic is
> parsed for validation and then **discarded**. Publishing `heat` to
> `infinitude/zone/2/mode/cmd` changes the mode of the entire system, including
> zone 1. This is a property of the Carrier Infinity platform — it has exactly
> one system mode — but the topic layout hides it.
>
> On a multi-zone system, expose mode as **one** item in your controller, bound
> to zone 1's topic, rather than one per zone. Otherwise your UI will show N
> independent mode controls that all fight over a single value.

Corresponding state topic: `<base>/zone/<N>/mode/state`, reporting the same
value for every zone (with `auto` rendered as `heat_cool`).

### 6.2 `<base>/zone/<N>/temp/cmd` — single setpoint

Payload: a number. What it does depends on the **current system mode**:

| Current mode | Effect |
|---|---|
| `heat` | Sets the heat setpoint only |
| `cool` | Sets the cool setpoint only |
| `auto` or `off` | Sets **both** the heat and cool setpoints to this same value |

That last row is almost never what you want — it collapses the deadband to zero
and will make the equipment hunt. **In `auto`, use `temp_low/cmd` and
`temp_high/cmd` instead.** The simplest robust policy for a controller is to
never use `temp/cmd` at all and always drive the low/high pair.

See [§6.5](#65-side-effect-shared-by-all-three-setpoint-commands) for the hold
side effect, which applies here too.

### 6.3 `<base>/zone/<N>/temp_low/cmd` — heat setpoint

Payload: a number. Sets the zone's heat setpoint (`htsp`) for the `manual`
activity. Valid in any mode.

### 6.4 `<base>/zone/<N>/temp_high/cmd` — cool setpoint

Payload: a number. Sets the zone's cool setpoint (`clsp`) for the `manual`
activity. Valid in any mode.

### 6.5 Side effect shared by all three setpoint commands

**Any setpoint write forces the zone into a temporary manual hold.** Infinitude
writes, atomically with the setpoint:

```
hold          = on
holdActivity  = manual
otmr          = <top of the next hour, rounded to the nearest quarter>
```

Consequences:

- The zone stops following its programmed schedule until that expiry time.
- `<base>/zone/<N>/preset/state` will change to `hold_until` as a result of a
  temperature command, even though you did not touch the preset topic. Do not
  treat this as an external change or you will create a feedback loop.
- The expiry is derived from the current hour **plus one**, with the current
  minute rounded to the nearest 15. At 14:07 the hold expires at 15:00; at
  14:23 it expires at 15:15. You cannot choose a different expiry over MQTT.
- To make a setpoint change permanent, publish the setpoint first and then
  publish `hold` to `<base>/zone/<N>/preset/cmd`, which rewrites `otmr` to
  `forever`. Order matters — doing it the other way round lets the setpoint
  command overwrite the permanent hold with a timed one.
- To hand the zone back to its schedule, publish `schedule` to
  `<base>/zone/<N>/preset/cmd`.

There is **no cross-validation** that the heat setpoint is below the cool
setpoint, and no minimum deadband is enforced. If your controller can produce
both values, enforce the ordering yourself before publishing.

### 6.6 `<base>/zone/<N>/fan/cmd` — fan

| Payload | Written to the thermostat as |
|---|---|
| `auto` | `off` |
| `low` | `low` |
| `medium` | `med` |
| `high` | `high` |

Note the mapping: the thermostat's `off` means "fan follows demand", which is
what everyone else calls `auto`. Infinitude translates in both directions, so a
controller only ever sees `auto`/`low`/`medium`/`high`.

> **Caveat: the fan command does not create a hold.** It writes the fan setting
> of the `manual` activity only, and unlike the setpoint commands it does *not*
> set `hold=on` / `holdActivity=manual`. If the zone is currently following its
> schedule (or holding a named activity such as `away`), the `manual` activity
> is not the active one and the change has **no observable effect** — and
> `<base>/zone/<N>/fan/state`, which reports the *active* activity's fan, will
> not change either.
>
> To make a fan change take effect, first put the zone into a manual hold —
> publish `hold` (or `hold_until`) to `<base>/zone/<N>/preset/cmd`, or publish
> any setpoint — then publish the fan value.

### 6.7 `<base>/zone/<N>/preset/cmd` — schedule and hold control

This is the only way to control hold/schedule behaviour over MQTT.

| Payload | `hold` | `holdActivity` | `otmr` (expiry) | Meaning |
|---|---|---|---|---|
| `schedule` | `off` | *(empty)* | *(cleared)* | Resume the programmed schedule |
| `none` | `off` | *(empty)* | *(cleared)* | Identical to `schedule` |
| `hold` | `on` | `manual` | `forever` | Permanent hold at the manual setpoints |
| `hold_until` | `on` | `manual` | next hour, quarter-rounded | Timed hold at the manual setpoints |
| `home` | `on` | `home` | **now**, quarter-rounded | Hold the `home` activity |
| `away` | `on` | `away` | **now**, quarter-rounded | Hold the `away` activity |
| `sleep` | `on` | `sleep` | **now**, quarter-rounded | Hold the `sleep` activity |
| `wake` | `on` | `wake` | **now**, quarter-rounded | Hold the `wake` activity |

Any other payload is silently ignored.

> **Known wart — the four named activity presets expire immediately.** For
> `home`, `away`, `sleep`, and `wake`, the expiry time is computed by rounding
> the **current** time to the nearest quarter hour, not the next hour's. The
> resulting `otmr` is therefore within ±7 minutes of now and often already in
> the past, so the thermostat drops the hold and resumes its schedule almost at
> once. Treat these four as unreliable. If you need a durable "away", set the
> setpoints you want with `temp_low`/`temp_high` and then publish `hold` for a
> permanent manual hold.

`hold`/`hold_until` hold the zone at whatever the `manual` activity's setpoints
currently are — they do not change the setpoints themselves. Publish setpoints
first if you want specific values.

Unlike the mode and setpoint commands, preset changes are written only to
Infinitude's stored configuration; there is no direct RS485 path for them even
when bus emulation is enabled (see [§7](#7-publish-timing-and-consistency)).

### 6.8 A note on `<base>/zone/<N>/action`

Read-only. Values map from the thermostat's `zoneconditioning`:

| Thermostat value | Published |
|---|---|
| `active_heat` | `heating` |
| `active_cool` | `cooling` |
| `prep_heat` | `preheating` |
| `prep_cool` | `cooling` |
| `idle`, anything else | `idle` |

Note that `prep_cool` is reported as `cooling`, not as a distinct "precooling"
state — the asymmetry with `prep_heat` is in the source.

### 6.9 `preset/state` derivation

Useful when reconciling your controller's state with reality:

- If the zone's `hold` is `on`:
  - and the held activity is `manual`:
    - with a real expiry time → `hold_until`
    - with `forever` or no expiry → `hold`
  - and the held activity is named (`home`/`away`/`sleep`/`wake`) → that name,
    regardless of expiry.
- If `hold` is `off`: the zone's *currently running* scheduled activity is
  reported if it is one of `home`/`away`/`sleep`/`wake`; otherwise `schedule`.

That last rule means **`preset/state` can read `home` or `away` while the zone
is simply following its schedule and is not held at all.** If you need to
distinguish "held at away" from "the schedule happens to be in its away period",
MQTT does not expose enough information; use the HTTP API
(`GET /systems/<id>/config`) for that.

## 7. Publish timing and consistency

State is published:

1. **8 seconds after Infinitude starts** — a full announce (availability,
   discovery, all state).
2. **Immediately after any local change** — an MQTT command, an HTTP `/api/*`
   call, or a change made in Infinitude's own web UI. This publish is
   **optimistic**: it reflects the configuration Infinitude has recorded, not
   what the thermostat has applied.
3. **On every broker reconnect** — a full announce.
4. **Every 60 seconds, if something changed.** The 60 s poller compares a
   watched set of fields (zone temperature, humidity, conditioning state, fan,
   current activity, hold, held activity, expiry, plus system mode) against the
   previous sample and republishes everything only when one differs.

> **The 60 s poller is suppressed while a change is pending.** From the moment a
> command is accepted until the thermostat has fetched the new configuration,
> the change-detection poll returns early and publishes nothing. During that
> window the only state you have is the optimistic publish from step 2.

### Propagation delay to the thermostat

The thermostat is the initiator: it polls Infinitude, Infinitude answers "I have
changes", and the thermostat then fetches and applies the new configuration.

| Situation | Typical delay before the equipment reacts |
|---|---|
| Normal | **12–20 seconds**, worst case ~40 s |
| With RS485 bus emulation (`EMULATE_SAM=1`) | Near-instant for **mode**, **setpoints**, and **fan** |

Mechanically: the thermostat polls roughly every 12 seconds. On the poll that
reports pending changes, Infinitude answers `serverHasChanges=true` and the stat
immediately fetches and applies the new configuration. So the delay is "time
until the next poll" plus the fetch — normally well under 20 s, but budget more
if the stat is busy.

RS485 emulation does **not** cover preset/hold changes — those always go through
the polled path.

**Implication for controllers:** do not implement "publish, wait, read back,
retry if unchanged" with a short timeout. The state topic republishes optimistically
within milliseconds, then may not change again for 20 s when the thermostat's
own report catches up. If you poll for convergence, allow 60 s.

### Optional Carrier cloud push

If `CARRIER_USER`/`CARRIER_PASS` are configured, every MQTT command also marks
the affected field dirty for an eventual push to Carrier's cloud (coalesced,
~5 s of quiet, at most once per 10 s). This is invisible over MQTT and never
blocks or fails a local command.

## 8. Zones

- Zones are **1-based**: `infinitude/zone/1/...`, `infinitude/zone/2/...`.
- The number is the zone's position in the thermostat's zone list, which on
  every observed system matches its zone id.
- **Only zones the thermostat reports as enabled publish state.** An Infinity
  system always describes 8 zone slots; a two-zone house publishes topics for
  zones 1 and 2 only.
- **Command topics are not bounds-checked.** `infinitude/zone/7/temp/cmd` on a
  two-zone system is accepted by the parser and passed down; at best it does
  nothing, at worst it raises an error inside Infinitude. **Only address zones
  you have observed publishing state.** Discover them by subscribing to
  `<base>/zone/+/current_temp` and noting which `<N>` arrive.
- Mode is global — see [§6.1](#61-basezonenmodecmd--system-mode).

## 9. Units and ranges

- **Units follow the thermostat.** Every value is passed through verbatim; there
  is no conversion anywhere in the MQTT path. If the thermostat is configured
  for Fahrenheit you get Fahrenheit, and if Celsius, Celsius. MQTT does not
  publish the unit on any state topic — it appears only inside the discovery
  payload (see Appendix A). Configure your controller's unit to match the
  thermostat and treat it as fixed.
- **Ranges are advertised but not enforced.** The discovery payload declares
  `min_temp: 40`, `max_temp: 99`, `temp_step: 1` — Fahrenheit-oriented values
  that are wrong for a Celsius system. More importantly, **nothing in the
  command path enforces them.** Infinitude will happily write `250` or `3` into
  the configuration, with unknown results at the thermostat.
- **Your controller must clamp.** Recommended guards before publishing:
  - Fahrenheit: clamp to 45–90, reject anything outside 40–99.
  - Celsius: clamp to 7–32.
  - Enforce `temp_low` < `temp_high` with a deadband of at least 2 °F / 1 °C.
  - Round to the resolution your thermostat accepts (whole degrees F, or
    half-degrees C).

## 10. What is NOT available over MQTT

These require Infinitude's HTTP API or web UI (`http://<host>:3000`):

| Capability | Where |
|---|---|
| Editing setpoints of non-`manual` activities (`home`, `away`, `sleep`, `wake`) | `PUT/POST /api/<zone_id>/activity/<activity_id>` |
| The weekly program / schedule (day and period definitions) | Web UI, or `GET/POST /systems/<id>/config` |
| Whole-house hold (as opposed to per-zone) | `POST /api/wholeHouse/hold` |
| Vacation mode | Web UI / HTTP config |
| An arbitrary hold expiry time | `POST /api/<zone_id>/hold` with an `until` parameter |
| Reading raw thermostat state (full `status`/`config` XML/JSON) | `GET /systems/<id>/status`, `GET /systems/<id>/config` |

The last row is worth remembering: over MQTT a hold can only expire at one of
two computed times. If you need "hold until 6pm", issue it over HTTP.

## 11. Worked examples

Using `mosquitto_pub` / `mosquitto_sub`. Substitute your broker, and add
`-u USER -P PASS` if authentication is configured. Note the absence of `-r` on
every publish — that is deliberate.

Watch everything:

```bash
mosquitto_sub -h 192.168.1.10 -v -t 'infinitude/#'
```

Discover which zones exist:

```bash
mosquitto_sub -h 192.168.1.10 -v -t 'infinitude/zone/+/current_temp' -W 3
```

Check that Infinitude is alive:

```bash
mosquitto_sub -h 192.168.1.10 -C 1 -t 'infinitude/status'
```

Set the system to heat (zone number is irrelevant, but must be a real zone):

```bash
mosquitto_pub -h 192.168.1.10 -t 'infinitude/zone/1/mode/cmd' -m 'heat'
```

Set zone 2's heat and cool setpoints (the safe way, works in every mode):

```bash
mosquitto_pub -h 192.168.1.10 -t 'infinitude/zone/2/temp_low/cmd' -m '68'
mosquitto_pub -h 192.168.1.10 -t 'infinitude/zone/2/temp_high/cmd' -m '76'
```

Make those setpoints a permanent hold (setpoint first, then hold):

```bash
mosquitto_pub -h 192.168.1.10 -t 'infinitude/zone/2/temp_low/cmd' -m '68'
mosquitto_pub -h 192.168.1.10 -t 'infinitude/zone/2/preset/cmd'   -m 'hold'
```

Return zone 2 to its programmed schedule:

```bash
mosquitto_pub -h 192.168.1.10 -t 'infinitude/zone/2/preset/cmd' -m 'schedule'
```

Force the fan to high on zone 1 (requires a manual hold to take effect):

```bash
mosquitto_pub -h 192.168.1.10 -t 'infinitude/zone/1/preset/cmd' -m 'hold'
mosquitto_pub -h 192.168.1.10 -t 'infinitude/zone/1/fan/cmd'    -m 'high'
```

Read back zone 1's setpoints and hold state:

```bash
mosquitto_sub -h 192.168.1.10 -v -W 2 \
  -t 'infinitude/zone/1/temp_low/state' \
  -t 'infinitude/zone/1/temp_high/state' \
  -t 'infinitude/zone/1/preset/state'
```

Clear a retained command you published by mistake (this is the fix if a
retained command keeps re-applying itself):

```bash
mosquitto_pub -h 192.168.1.10 -r -n -t 'infinitude/zone/1/temp/cmd'
```

## 12. Implementation checklist for a controller

- [ ] Subscribe to `<base>/status` and mark everything stale on `offline`.
- [ ] Discover zones from observed `<base>/zone/+/current_temp` topics; do not
      assume zone count.
- [ ] Publish **all** commands non-retained, QoS 0.
- [ ] Bind mode as a single system-wide control, not one per zone.
- [ ] Prefer `temp_low`/`temp_high` over `temp`; if you do use `temp/state`,
      handle the literal string `None`.
- [ ] Clamp and order setpoints before publishing; nothing downstream will.
- [ ] Expect `preset/state` to flip to `hold_until` after any setpoint command,
      and suppress the resulting echo so it does not loop.
- [ ] Allow up to 60 s for state to converge; do not retry aggressively.
- [ ] Put a manual hold in place before expecting a fan command to do anything.
- [ ] Avoid the `home`/`away`/`sleep`/`wake` presets; they expire immediately.
- [ ] Treat a silent non-response as a rejected payload — there is no error
      channel.

## Appendix A: Home Assistant discovery

Skip this section entirely unless you also run Home Assistant against the same
broker. It documents behaviour that is harmless but visible to other subscribers.

Infinitude publishes retained JSON discovery configs under the discovery root
(`MQTT_PREFIX`, default `homeassistant`):

| Topic | Entity |
|---|---|
| `<prefix>/climate/infinitude_zone_<N>/config` | One climate entity per enabled zone |
| `<prefix>/sensor/infinitude_oat/config` | Outdoor Temperature (°F) |
| `<prefix>/sensor/infinitude_filtrlvl/config` | Filter Level (%) |
| `<prefix>/sensor/infinitude_uvlvl/config` | UV Lamp Level (%) |
| `<prefix>/sensor/infinitude_humlvl/config` | Humidifier Level (%) |
| `<prefix>/sensor/infinitude_ventlvl/config` | Ventilator Level (%) |
| `<prefix>/sensor/infinitude_humid/config` | Humidifier State |

All entities share one device: identifier `infinitude`, name `Infinitude`,
manufacturer `Carrier`, model `Infinity`. The climate payload declares
`modes`, `fan_modes`, `preset_modes`, `optimistic: true`, `temp_step: 1`,
`min_temp: 40`, `max_temp: 99`, a `temperature_unit` derived from the
thermostat's own unit setting, and the availability topic from
[§3](#3-availability). **The discovery payload is the only place the
temperature unit is published.**

Zones that are not enabled receive a retained **zero-length** payload on their
config topic, which deletes any stale entity. A subscriber watching
`<prefix>/#` will therefore see empty messages on config topics for zones 3–8 on
a two-zone system; this is normal.

Infinitude also **subscribes** to `<prefix>/status` and, on receiving `online`
(case-insensitive), re-publishes availability, all discovery configs, and all
state. This is Home Assistant's birth message. A non-HA controller should not
publish to this topic; if it does, it will trigger a full re-announce. Note the
`MQTT_PREFIX` == `MQTT_TOPIC` collision warning in [§2](#2-connection-and-configuration).

Note two cosmetic bugs in the sensor configs, in case they confuse you:
`infinitude_oat` is hardcoded to `°F` even on a Celsius system, and no sensor
declares a `device_class` or `state_class`.
